# 13 - Android port plan

Status: proposal, 2026-10-26. Author: Android Developer (board). Read-only research of `main.js`, `src/`, `renderer/`, `test/`; nothing built or run.

## 0. What we are porting (measured)

| Part | Files | Lines | Nature |
|---|---|---|---|
| Pure logic, already takes an injected `get(url)` | `src/music.js`, `src/tree.js`, `src/stamps.js`, `src/spotify.js` (helpers), `src/cache.js`, `src/countries.js`, `src/links.js` | ~1,600 | Query building, guards, ordering, matching. Tested against recorded JSON in `test/fixtures/`. |
| Taste engine | `renderer/features.js` | 183 | FFT, 14-dim vector, score/rank/explain/pickSource. Pure. |
| Data | `renderer/genre-data.js` (1,142 genres), `renderer/stamp-data.js` (catalogue factory) | ~1,380 | Generated by `scripts/build-genre-stamps.js`, plus hand-written stamp tables. |
| Platform glue | `main.js`, `preload.js`, `src/net.js`, `src/store.js` | ~400 | IPC, pacing, disk cache, profile file, safeStorage. |
| UI + orchestration | `renderer/app.js`, `index.html`, `styles.css`, `tint.js` | ~2,780 | DOM, Blind Test queue/pool logic mixed into the UI, 8 schemes x light/dark. |
| Tests | `test/*.test.js` | ~1,750, 141 tests | `node --test`. The spec for the port. |

Two facts drive the plan: the logic modules are already platform-free (they take `get`), and the Blind Test orchestration (pool of ~6, misfit counter, bring-back) lives inside `app.js` and must be rewritten whichever route we take.

## 1. Recommendation

| Option | Effort to first sideload APK | Effort to Play closed test | Gains | Loses |
|---|---|---|---|---|
| **A. Capacitor wrap** of the renderer | 2-3 dev-weeks (board estimate), realistically **3-5** | 4-6 | One codebase; desktop features appear on the phone for free; fastest. | `src/` runs in Node today and must move into the WebView anyway (Deezer has no CORS, so CapacitorHttp; `fs` cache to a plugin). Background playback is fragile: the WebView throttles timers when the screen is off, so the Blind Test queue stalls, and lock-screen controls need a native media plugin anyway (+~1 week). The 1,040 px desktop layout needs a full mobile reflow. Spotify loopback login does not work on a phone. |
| **B. Native Kotlin + Compose**, logic ported to Kotlin | **6-7** | **9-11** | Real Media3 service (background, notification, lock screen, Bluetooth/Auto buttons), lower battery (no WebView, native decode), proper touch UI, Keystore, process-death safe state. | Two codebases. Every desktop logic change needs a port ticket. 2-3x the effort of A. |
| **C. Hybrid**: Compose shell + Media3, shared JS logic in QuickJS | 5-6 | 8-9 | Logic stays single-source. | Three runtimes (Kotlin, QuickJS, Node), async bridge for `get`, Node shims (`require`, `crypto`, `Buffer`), harder debugging, interpreter-speed FFT. The saving over B is only the ~1,800 lines of pure logic, which is the easiest part to port. |

**Pick: B, native Kotlin + Compose**, with the drift controls in section 2.4.

Why, against the cheaper Capacitor path: the phone use case is "headphones on, screen off, rate from the lock screen or notification", and that is exactly what a WebView does worst. In A we would still write a native media plugin, a native HTTP path, a native secure store and a native OAuth redirect, then fight WebView background throttling. Those are four of B's hardest parts, done without B's payoff. The extra cost of B is about 5-6 dev-weeks, mostly UI. What is gained: reliable background playback, a lock-screen Love/Skip, one preview download feeding both the player and the fingerprint, and a UI built for thumbs.

When A is still right: if you only want the app on your own phone soon and are happy with "screen on while using it", A at 3-5 weeks is the better deal. That is open question 1.

## 2. Architecture

### 2.1 Stack

Kotlin 2.x, Jetpack Compose + Material 3 (as a component base, re-themed), single-activity, Navigation Compose, MVVM with `ViewModel` + `StateFlow`, coroutines, OkHttp, kotlinx.serialization, Media3 (ExoPlayer + MediaSessionService), DataStore, Room (cache only), Coil (covers). minSdk 26, targetSdk current. No DI framework: one `AppContainer` object (a handful of singletons does not need Hilt).

### 2.2 Modules (Gradle)

| Module | Contents | Android deps |
|---|---|---|
| `:core` (pure Kotlin/JVM) | Ports of `music`, `tree`, `stamps`, `features`, `stamp-data`, `cache` rules, `store` validators, `spotify` helpers. Everything takes `suspend (String) -> Json` like the JS takes `get`. | none |
| `:data` | `Net` (allowlist, per-host pacer, retries, Room cache), `ProfileRepository` (DataStore), `SpotifyClient`, `PreviewDecoder` (MediaCodec) | Android |
| `:playback` | `PlaybackService : MediaSessionService`, custom session commands Love/OK/Skip | Media3 |
| `:app` | Compose screens, ViewModels, theme | Compose |

`:core` being JVM-only means its tests run with plain `./gradlew :core:test`, fast, no emulator.

### 2.3 How each file maps

| Desktop | Android | Action |
|---|---|---|
| `src/net.js` | `data/Net.kt` | **Rewrite**, same rules: host allowlist, `GAP` per host (MB 1,500 ms, iTunes 3,000, Deezer 125, Wikipedia/Wikidata 200) via one `Mutex` + timestamp per host, in-flight de-dup map, MB 503 backoff 2/4/6/6/6 s, Deezer `code 4` retry, 15 s timeout, audio host allowlist + 2 MB cap, Spotify-only `send`. |
| `src/cache.js` | `core/CacheRules.kt` + Room table `(url PK, t, body)` | **Port** TTLs and prune (5,000 entries / 20 MB). Room instead of one JSON file: no 20 MB parse at cold start. |
| `src/store.js` | `core/ProfileValidators.kt` + DataStore | **Port** validators 1:1 (they guard the import path too). |
| `src/music.js`, `src/tree.js`, `src/stamps.js` | `core/Music.kt`, `core/Tree.kt`, `core/Stamps.kt` | **Port**. Streaming `emit(row)` becomes `Flow<Row>`. `MB_BUDGET`, `CAP`, `MORE` unchanged. |
| `src/spotify.js` | `core/SpotifyRules.kt` (pkce, pickIsrc, pickStrict, chunk, errorFor) + `data/SpotifyClient.kt` | **Port helpers, rewrite transport** (no loopback server; see 6). `pickDevice` is dropped (see 4.3). |
| `src/countries.js`, `src/links.js` | `core/` | Port (tiny). |
| `renderer/features.js` | `core/Features.kt` | **Port** line for line (DoubleArray FFT). Decoding is new: `PreviewDecoder` uses `MediaExtractor` + `MediaCodec` to PCM, downmixes to mono, resamples to 22,050 Hz, takes the middle 20 s, exactly as `app.js` `fingerprint()` does with `OfflineAudioContext`. |
| `renderer/genre-data.js`, `renderer/stamp-data.js` | `assets/genre-atlas.json`, `assets/stamp-data.json` | **Reuse data, not code**. `scripts/build-genre-stamps.js` gains a `--json` output (a few lines); stamp tables are dumped once by a tiny node script that `require`s `stamp-data.js`. Desktop stays the single source; Android reads the JSON. |
| `renderer/app.js` | ViewModels per tab | **Rewrite**. The Blind Test pool/misfit/bring-back logic is pulled out into `core/BlindQueue.kt` (pure, testable) instead of living in the UI as it does today. |
| `renderer/styles.css` scheme blocks | `ui/theme/Schemes.kt` | **Generate**: the 8 schemes are already `#rrggbb` pairs that `test/contrast.test.js` parses; the same parser can emit Kotlin. |
| `main.js`, `preload.js` | n/a | Gone (no IPC). |

### 2.4 Keeping desktop and Android from drifting

1. **Shared fixtures**: `:core` tests read `test/fixtures/*.json` directly (Gradle `sourceSets` points at the repo's `test/fixtures`). Same recorded MusicBrainz/Deezer/iTunes bodies, same expected outputs.
2. **Golden outputs**: a node script `scripts/golden.js` runs the JS functions over the fixtures and writes `test/golden/*.json` (tree nodes, stamp song order with a seeded `rand`, spotify picks, store validation of bad profiles). Kotlin tests assert equality. When desktop logic changes, golden files change in the same commit, and the Kotlin test fails until ported. Drift becomes a red test, not a surprise.
3. **Taste-engine parity**: `features.test.js`'s synthetic signals become golden vectors (tolerance 1e-9, pure maths). For real audio, one short preview-length fixture decoded on both sides must give vectors within distance 0.02; otherwise imported desktop ratings would score differently on the phone.
4. **Seeded randomness**: every JS function that takes `rand` keeps that parameter in Kotlin, so golden runs are deterministic.
5. Rule for the board: logic changes land on desktop first, with a fixture and golden update; the Android port is a follow-up ticket.

Which tests to port: all of `music`, `tree`, `stamps`, `features`, `store`, `store-genre`, `net` (pacer/backoff with a fake clock), `spotify`, `genre-atlas`, `links`. Skip `contrast` (replaced by a Kotlin contrast test over the generated theme), `tint`, `about`, `genre-build` (build script stays node).

## 3. Navigation skeleton

Screen-by-screen UI, visual identity and touch patterns: see **docs/15-android-ui.md** (Designer). What the architecture assumes:

- Single activity, Navigation Compose, **bottom bar with 4 destinations**: Blind Test (Home's intro and "continue where you left off" become its start state), Crate Dig, Family Tree, Saved. Preferences opens from a gear in the top bar.
- A **mini player** above the bottom bar, bound to the Media3 session, expanding to a full player sheet.
- One ViewModel per destination; the back stack and each tab's state survive process death (`SavedStateHandle`).
- Theme: Material 3 as the component base with custom `ColorScheme`s for the 8 schemes x light/dark, generated from `renderer/styles.css` (section 2.3), and the bundled Big Shoulders Display font. Not stock Material.

## 4. Playback

### 4.1 Previews
- One `ExoPlayer` in a `MediaSessionService`. Audio focus and becoming-noisy (headphones unplugged) handled by Media3 with `setAudioAttributes(..., handleAudioFocus = true)` and `setHandleAudioBecomingNoisy(true)`.
- **One download per preview**: `Net.audio()` saves the bytes (max 2 MB) to `cacheDir/previews/`; ExoPlayer plays that file and `PreviewDecoder` fingerprints the same file. Today the desktop downloads twice (once for `<audio>`, once for the fingerprint). Deezer URLs expire after ~15 min, so the cache is keyed by track id and short-lived (delete on next pool refill).
- Fingerprinting runs on `Dispatchers.Default`, max 2 at a time, inside the ViewModel scope; the service stays alive only while playing.

### 4.2 MediaSession, notification, lock screen
- `MediaSessionService` + default `MediaNotification.Provider`: play/pause on lock screen, notification, Bluetooth and Wear.
- Custom session commands **Love** and **Skip** as notification buttons (`CommandButton`), so rating works with the screen off. In Blind Test the session metadata is "Mystery track" with no artwork until rated (principle 1: judge the sound, not the name).
- Queue auto-advance in Blind Test keeps working in the background because the queue is driven by the service-bound ViewModel/repository, not WebView timers.

### 4.3 Spotify handoff (checked October 2026)
Current options on Android:
- **Deep link** `spotify:track:<id>` via `ACTION_VIEW` (package `com.spotify.music`). No SDK, opens and plays in the Spotify app. Recommended for "Play in Spotify".
- **App Remote SDK** (Spotify Android SDK, still labelled Beta, needs the Spotify app installed and the APK's signing fingerprint registered in the dashboard). Gives player state; not needed for v1. Skip.
- **Web API `/me/player/play`** (what desktop uses): needs Premium and an active device; on a phone the Spotify app is often not "active" until opened, so the deep link is more reliable. Dropped on Android.

Flow: connected user -> Web API search by ISRC (existing `pickIsrc` / `pickStrict`, search limit 10 since the February 2026 changes) -> deep link to the track. Not connected -> deep link to a Spotify search for "artist title" (no auth). Playlist export stays Web API: `POST /me/playlists`, `/playlists/{id}/items` in chunks of 100 (already ported in `spotify.js`). Spotify audio is never analysed.

## 5. Data and network

- **Profile: DataStore** with a kotlinx.serialization serializer over the *same* JSON schema as `profile.json` (likes, heard, stamps, rarity, adventure, ratings <= 500, prefs, last, back). It is one small document, written atomically, read as a `Flow`; Room would add a schema for no gain. Validators from `store.js` run on every read and import.
- **Import desktop profile**: Preferences -> "Import desktop profile" opens the system file picker (SAF) for a `profile.json` the user copies over (USB, Drive). Run through the validators, show a summary ("312 loves, 41 ratings"), then merge (union likes/heard by id, sum stamp counts, newer ratings win, keep 500). Export is the reverse, via share sheet. Never read anything automatically; never touch the real desktop profile during development (use a copy in the worktree's `test/fixtures`).
- **Cache: Room**, TTLs and prune from `cache.js`, pruned on app start and when the app goes to background.
- **MusicBrainz from a phone**: MB limits per IP. Each phone has its own IP, but mobile carriers put many users behind one CGNAT address, so expect more 503s than on home broadband. Keep the 1.5 s gap and the 6-try backoff, keep `MB_BUDGET = 60` per tree, de-dup in-flight URLs, and show progress ("asking MusicBrainz, 12 of 30") because Crate Dig / Family Tree are slow by design. The User-Agent currently carries a personal email; for any public build switch it to a project contact URL (MB requires a contact, not necessarily an email).
- **Offline**: `ConnectivityManager` callback -> banner. Saved, profile, atlas, cached MB answers all work offline; previews do not (no streaming, and Deezer URLs expire). Blind Test shows "needs a connection" instead of spinning.
- **Battery and data**: one download per preview (4.1); fingerprint pool of 6 on Wi-Fi, 3 on metered networks (toggle in Preferences); no background sync, no WorkManager, nothing runs when not playing; covers through Coil with a 50 MB disk cache at 300 px; cancel all in-flight work when a tab's ViewModel is cleared. Rough cost: a preview is ~0.5-1 MB, so a 30-mystery session is ~25 MB on Wi-Fi.
- **Memory**: decode at most 20 s mono at 22,050 Hz (~1.8 MB float), two at a time; atlas JSON (~110 KB) loaded lazily once.

## 6. Security

- **No secrets in the APK.** The Spotify Client ID is user-entered in Preferences (as on desktop, validated `^[0-9a-f]{32}$`); PKCE needs no client secret. No other keys exist.
- **PKCE on Android**: Custom Tab to `accounts.spotify.com/authorize` with S256 challenge and `state` (port `pkce()` / `stateOk()`). Redirect URI: a custom scheme such as `stumble-auth://spotify` caught by an intent filter on a single `exported` activity. App Links (https) would need a domain with `assetlinks.json` that we don't have. Custom-scheme interception by another app is mitigated by PKCE (the verifier never leaves the app) plus `state`. The user adds this second redirect URI in their Spotify dashboard; `docs/11-spotify-setup.md` gets an Android section. Verify Spotify still accepts custom-scheme redirects when implementing.
- **Token storage**: the refresh token is encrypted with an AES-256-GCM key in the **Android Keystore** (non-exportable) and the ciphertext stored in DataStore. Not `EncryptedSharedPreferences`: `androidx.security:security-crypto` is deprecated. Access tokens live in memory only (as on desktop).
- **Backup**: `dataExtractionRules` exclude the token store (a Keystore-encrypted blob can't be decrypted on a new device anyway); the profile may be backed up.
- **Network**: `networkSecurityConfig` with cleartext disabled; the host allowlist from `net.js` stays the single gate; only Spotify hosts ever get an `Authorization` header; preview fetches allow only the CDN hosts, no redirects, 2 MB cap.
- External links go through the `links.js` allowlist before `ACTION_VIEW`.

## 9. Open questions for the user

1. **Personal or public?** If the APK is only for you (and up to 4 friends), Capacitor at 3-5 weeks may be enough. Native is recommended if the phone will be your main way to use Stumble, or if a Play release is the goal.
2. **Is desktop still the primary app?** If desktop logic keeps changing weekly, every change costs an Android port ticket (made safe by golden tests, but not free).
3. **Profile sync**: is one-off import/export via a file enough, or do you want the two devices to stay in sync (that would need a sync service, which is out of scope here)?
4. **Spotify on the phone**: is "open in the Spotify app" (deep link) enough, or do you need in-app control of Spotify playback (App Remote SDK, still Beta)?
5. **Mobile data**: OK to fingerprint previews on mobile data (~25 MB per 30-track session), or Wi-Fi only by default?
